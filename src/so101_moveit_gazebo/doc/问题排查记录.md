# SO101 Gazebo 接入问题排查记录

记录 so101_moveit_gazebo 包在 mock → Gazebo 接入过程中遇到的全部问题：现象、定位过程、解决办法。

环境：ROS 2 Humble + Gazebo Classic 11 + WSL2/WSLg，colcon 工作区 `so101_moveit_gazebo/`。

---

## 1. Gazebo 中机器人"隐形"

**现象**
spawn_entity 日志显示 `Successfully spawned entity [so101]`，但 Gazebo 界面里看不到机器人。

**定位**
URDF 里 mesh 用的是 `package://so101_moveit_gazebo/urdf/assets/xxx.stl`。Gazebo 会把 `package://` 转成 `model://` 再解析，而 Gazebo Classic 只按 `GAZEBO_MODEL_PATH` 找 `model://` 资源，找不到就静默不显示（gzclient 的 `InsertModelWidget.cc: Missing model.config` 报错是线索之一）。

**直接证据（Gazebo 私有日志）**
Gazebo Classic 把全部消息（包括不往 stdout 打的 Err）写进自己的日志文件，不走 ROS 日志系统，所以 launch 终端里看不到任何报错：
```
$ grep -a "Failed to find mesh" ~/.gazebo/server-11345/default.log
[Err] [MeshShape.cc:64] Failed to find mesh file [model://so101_moveit_gazebo/urdf/assets/sts3215_03a_v1.stl]
```
`model://so101_moveit_gazebo/...` 证实了转换机制：spawn 时 `package://` 被转成 `model://`，而包目录不在 `GAZEBO_MODEL_PATH` 里，逐文件解析失败。日志里有 ANSI 转义字节，grep 要加 `-a`。查看方式：
- `~/.gazebo/server-11345/default.log`：gzserver（物理端）；`~/.gazebo/client-11345/default.log`：gzclient（渲染端），mesh 报错多在这里
- `11345` 即启动日志里 `Connected to gazebo master @ http://127.0.0.1:11345` 的端口；每次启动覆盖，可 `tail -f` 实时跟踪

**解决（演进过程）**
1. 先在 launch 里用 `SetEnvironmentVariable` 把包的上级 share 目录加进 `GAZEBO_MODEL_PATH`（提交 `d1085f9`）——能用但污染全局环境；
2. 最终方案：xacro 里 mesh 路径全部写成 `$(find so101_moveit_gazebo)/urdf/assets/xxx.stl`，xacro 展开时直接替换成绝对路径，launch 里的环境变量设置也删掉了（提交 `af54e15`）。后来证明裸绝对路径 RViz 读不了（见问题 10），现已统一改为 `file://$(find ...)` 前缀，Gazebo/RViz 都兼容。

**同类现象另一层根因（2026-09-10 补充）：spawn 时序导致客户端丢视觉**
现象与 #1 相同（隐形）但 mesh 路径完全正常：Models 列表有 so101、物理数据（`/model_states`、关节、夹取）全部正常、服务端日志无任何 mesh 报错，同一份 SDF 用服务 spawn 的副本却能正常渲染。
定位：launch 中 `spawn_entity` 在 gzclient 尚未连上就绪时生成模型，客户端场景没收到/丢了该模型的视觉元素（列表和物理状态是后连上时从服务器补的，视觉不同步）。
排查手法：用两个对照实验区分"模型内容问题"vs"实例同步问题"——spawn 一个引用同 STL 的简单探针（正常→网格管线没问题），再用 `gz sdf -p` 转换的 SDF 静态副本 spawn（正常→模型内容没问题），则必是原实例同步丢了。
解决：`ros2 service call /delete_entity ...` 删掉重 spawn（或干脆重拉 launch）。
**注意**：gazebo_ros2_control 插件挂在模型里，删模型 = 删控制器管理器，重 spawn 后必须重新链式加载三个控制器（joint_state_broadcaster → arm → gripper），否则 `/joint_states` 静默无数据。

## 2. Spawn 失败：`Entity [so101] already exists`

**现象**
```
[spawn_entity]: Spawn status: Entity [so101] already exists.
[spawn_entity]: Spawn service failed. Exiting.
```

**定位**
上一次运行的 gzserver 没退干净，仍占用 11345 端口。新启动的 gzserver 连不上 master 会**静默死亡**（launch 日志里看不到 Gazebo 版本 banner 是明显线索），spawn_entity 连到的是旧实例，旧实例里已经有同名机器人。

**解决**
重跑前清残留进程：
```bash
pkill -x gzserver; pkill -x gzclient
```
注意不要用 `pkill -f`（模式匹配到自己命令行会杀当前 shell），也不要把 pkill 和启动 gazebo 的命令写在同一条里。

## 3. KDL 警告：根链接带惯性

**现象**
robot_state_publisher 启动时：
```
[WARN] [kdl_parser]: The root link base_link has an inertia specified in the URDF,
but KDL does not support a root link with an inertia.
```

**定位**
KDL  kinematics 求解器不允许根链接带惯性属性，而 URDF 的根链接（base_link）写了 `<inertial>`。

**解决**
加一个无质量的虚链接 `world` 作为根，用 fixed 关节把 `base_link` 挂上去。KDL 只限制根链接，非根链接带惯性没问题，警告消除。该修改只加在 `so101_gazebo.urdf.xacro`（Gazebo 版），mock 版保持干净。

## 4. 机器人在 Gazebo 中缓慢"移动"（下沉/歪斜/漂移）

**现象**
机器人能 spawn 出来，但放着不动会逐渐下沉、姿态歪斜，整机像在慢慢移动。

**定位**
URDF 里关节只声明了 `position` 命令接口，而 Gazebo 物理引擎只接受力矩（effort）。`gazebo_ros2_control/GazeboSystem` 内部用一个 PID 把位置误差换算成力矩；**不指定增益时默认值非常弱**，输出的保持力矩抵不过重力，关节被持续拉开。可用 `ros2 topic echo /joint_states` 看到无指令下 position 持续变化来确认。

**解决（当前状态）**
- 在 `<command_interface name="position">` 下加 `<param name="p/i/d">` 可显式指定增益（提交 `af54e15` 加过 p=25, i=0.5, d=5）；
- 应要求暂时移除，先观察 world 固定后的效果（提交 `ab93113`）。
- 调参方向：还下垂→加大 p；振荡/抖动→加大 d；长期静态偏差→加大 i。
- PID 原理与调参方向（P=刚度/I=消静差/D=阻尼）：详见 `../so101_moveit_mujoco/src/so101_moveit_mujoco/doc/control_basics.md` 第 1 节；力矩 PID 路线在本包的实验证伪记录见第 11 条。

注意：world 固定只解决"整机倾倒/滑动"，**不解决关节下垂**，两者互补。

## 8. Gazebo 界面"卡住"（假死/加载慢）

**现象**
启动后 Gazebo 界面长时间白屏/卡住；或界面能开但场景不刷新——spawn 的物体看不到、手臂动了画面不动（数据侧一切正常，`/model_states` 有位姿、控制器 active）。

**定位（两层原因）**
1. WSLg 下 Gazebo 客户端渲染慢，首次加载 mesh/材质更慢，属于性能问题而非死锁；
2. **gzclient 联网拉模型列表卡死 GUI 主线程**：gzclient 启动时要从 `models.gazebosim.org` 下载在线模型库列表填 Insert 面板，网络不通（国内常见）时 curl 反复重试，GUI 长时间不渲染不刷新。特征：`~/.gazebo/client-11345/default.log` 里 `ModelDatabase.cc Unable to get model name` 刷屏 + `libcurl: (35) SSL routines::unexpected eof`。

**解决**
- launch 里已加 `SetEnvironmentVariable('GAZEBO_MODEL_DATABASE_URI', '')`（在 gzclient 启动前生效），禁掉在线模型库；本包模型全部本地，无副作用；
- 手动启动时也可以 `GAZEBO_MODEL_DATABASE_URI="" ros2 launch ...`；
- 多等一会；日常开发建议不用盯着 Gazebo 界面看模型——用 RViz 看（数据走 TF/joint_states，流畅得多），Gazebo 只当后台物理引擎。

## 9. 控制器加载时机：spawn 完成后再起 controller

**现象/背景**
controller_manager 是 `gazebo_ros2_control` 插件在 spawn 之后才启动的，若 launch 里同时 unconditional 加载 controller，会报服务不存在。

**解决**
用 `RegisterEventHandler + OnProcessExit` 链式触发：spawn 退出 → 加载 joint_state_broadcaster → 加载 arm_controller → 加载 gripper_controller。`ros2 control load_controller` 命令本身会等 `/controller_manager` 服务就绪，链式保证顺序即可。用户后来额外加了 `TimerAction(period=10.0)` 延迟 spawn，进一步规避竞争。

## 10. RViz 报错 `Error retrieving file`（裸绝对路径 mesh，Gazebo 却正常）

**现象**
`so101_display.launch.py` 启动时 RViz 对所有 STL 报：
```
[rviz2]: Error retrieving file [/home/.../install/so101_moveit_gazebo/share/so101_moveit_gazebo/urdf/assets/xxx.stl]:
```
（冒号后错误信息为空）。同时 `so101_gazebo.launch.py` 加载同一个模型完全正常。文件确实存在、是合法的 binary STL（文件大小 = 84 + 50 × 三角面数）。

**定位**
- xacro 里 mesh 写 `$(find so101_moveit_gazebo)/urdf/assets/xxx.stl`，展开成**裸绝对路径**；
- RViz 把 URDF 里的 filename 原样传给 `resource_retriever`，后者（Humble 3.1.3）只识别 `package://`（转 file://）和 `file://`，**裸绝对路径原样丢给 libcurl，没有 URL scheme** → curl 返回 `CURLE_URL_MALFORMAT (3)`；
- libcurl 在 URL 校验阶段就失败，**不会发起任何文件 syscall**（strace 看不到 openat），所以报"retrieving"而非"reading"；
- Gazebo 自己直接读裸文件路径，不经过 resource_retriever，所以不受影响；
- 报错信息为空是因为 resource_retriever 把空的 curl error buffer 直接抛了出来，极具迷惑性。

**验证手段**
- `LD_PRELOAD` 钩住 `curl_easy_perform` 打印返回码，看到 `ret=3 (URL using bad/illegal format or missing URL) url=/home/...stl`（注意 URL 没有 `file://` 前缀），实锤；
- python 版 `resource_retriever.get('file://...')` 正常，说明文件和库都没问题，差别只在 scheme。

**解决**
mesh 路径统一加 `file://` 前缀：`filename="file://$(find so101_moveit_gazebo)/urdf/assets/xxx.stl"`（sed 只改含 `/assets/` 的行，`<xacro:include>` 的行不能加）。RViz（curl）和 Gazebo（file:// URI）都能解析。
教训：问题 1 把 mesh 从 `package://` 改成 `$(find)` 裸绝对路径时，以为"Gazebo/RViz 都能读"，实际只对 Gazebo 成立，RViz 一直裸奔到这次才暴露。

## 11. MuJoCo 对比引出的"夹爪下垂"复查：默认 position 接口其实锁得很死，PID 强增益路线不可行（2026-09）

> 原理背景（PID 三项、静差、为什么同参数一边稳一边炸）：见 `../so101_moveit_mujoco/src/so101_moveit_mujoco/doc/control_basics.md` 第 1、3 节。本条只记排查事实。

**现象**
同一台 SO-101，MuJoCo 版启动后零位保持刚性；Gazebo 版启动时夹爪/手腕会垂一下再恢复，怀疑与问题 4 同源（默认增益弱）。

**定位（读源码 + 实测）**
[Humble 源码](https://github.com/ros-controls/gazebo_ros2_control/blob/humble/gazebo_ros2_control/src/gazebo_system.cpp)：`position` 接口**无 PID 参数时走 `POSITION` 传送模式**（`SetPosition` 直接摆到指令位，非力矩伺服）；写 joint 级 `pos_kp/pos_ki/pos_kd`（前缀 `"pos_"`）才切 `POSITION_PID` 力矩模式。

实测（shoulder_lift=-1.2 / elbow_flex=+1.2 位形静止 10s）：传送模式位形两次采样差 ~1e-10——**控制器激活后不存在下垂**。可见下垂只在 spawn 后 ~1s 窗口期（控制器未激活，`hold_joints` 仅 `SetVelocity(0,0)` 弱保持）；MuJoCo 无此窗口因其 actuator 从第一步就在 hold。

**失败实验（力矩 PID 路线，均不可用）**
| 配置 | 结果 |
|---|---|
| pos_kp=50, kd=1 @ CM 100Hz | 剧烈振荡（wrist 速度 ±150 rad/s），远超显式离散稳定域 |
| update_rate 500Hz | 控制器激活超时（`Switch controller timed out after 5s`，本机无 RT 跑不稳） |
| pos_kp=20, kd=1 @ 500Hz | 仍大幅振荡 |

结论：轻量臂（J~1e-4）在 100~500Hz 显式力矩控制下稳定 kp<10，重力静差不可接受；力矩 PID 需更高频率 + RT，性价比低。**维持默认传送模式**。

**解决**
spawn 前等待 5s → 2s（`spawn_entity` 内部自等服务，短延时安全），下垂窗口进一步压缩；PID 与 update_rate 维持原状。

**教训**
- 改增益前先读插件源码确认控制模式语义——这里的默认模式是 teleport，比 PID 还"硬"；
- `af54e15` 加 PID、`ab93113` 撤 PID 的反复，根源是力矩模式在这类小臂上需配合高控制频率，单独调增益无解；
- colcon 增量安装偶发不刷新 install 里的 xacro，行为与源码不符时先 `rm -rf build/<pkg> install/<pkg>` 全量重建再下结论。


## 12. position 模式夹爪抓不起方块：传送模式无接触力，换 effort 控制器（2026-09）

**现象**
夹爪方块放到钳口之间、发闭合指令（position 1.5 rad），方块不是被碰飞就是穿透掉地，无论怎么调摩擦参数都"抓不中"。

**定位**
第 11 条已确认 position 接口是传送模式：`SetPosition` 直接把关节摆到目标角，钳口瞬间跳过与方块的接触过程，不产生任何夹持力；闭合后再抬手臂，方块留在原地。

**解决（已实测验证）**
1. `so101_hand.ros2_control.xacro`：gripper 命令接口 position → **effort + position**（保留 position 便于 display/mock 场景）;
2. `so101_ros2_control.yaml`：`so101_gripper_controller` 类型 → `effort_controllers/JointGroupEffortController`（package.xml 加 `effort_controllers` 依赖）;
3. 新增 `objects/cube.urdf`（2cm/20g/mu=1.0），launch 里 `spawn_entity -file` 生成在钳口之间。

**实测数据**
- 闭合 `effort 0.1`（N·m，关节上限 10）：钳口到达上限，方块被夹住；
- 抬手臂 wrist_flex -0.48→-0.85：方块 z 0.167→0.228 跟随上升，手臂放下、发 `-0.1` 张开正常；
- 对比基线：position 模式同样流程方块两次均掉地（z 回到 0.01）。

**注意**
- effort 正值=闭合方向（关节 upper limit 侧），负值=张开；符号与 URDF 关节轴向一致，换模型需重新确认；
- 夹紧后**不要直接给 0**：0 力矩靠摩擦自锁，重物的静载可能让钳口缓缓张开，建议维持小正 effort 保持夹持；
- 方块 spawn 坐标按机械臂初始位形标定（launch 里 -x 0.303 -y 0.009 -z 0.21），改初始位形后需同步改；
- **腕关节会漂移**：夹爪 effort 闭合接触方块/限位时，反作用力会把 wrist_flex/wrist_roll 从保持位推开（实测 roll 漂过 1.4 rad），且每次漂的位置不一样——固定 spawn 坐标随之失效。`grasp_cube.py` 的应对：每次试验先发轨迹回标定位形再 spawn 方块；手动试验同理，spawn 前先确认臂姿。


## 13. 夹爪控制器激活报 `Not existing: gripper/effort`：残留 robot_state_publisher 给了旧 URDF（2026-09）

**现象**
重跑 launch 时 `so101_gripper_controller` 激活失败：`Could not switch controllers since prepare command mode switch was rejected` + `Not existing: [gripper/effort]`。xacro 源码和 install 里的文件都确认有 effort 接口。

**定位**
gazebo_ros2_control 插件启动时从 `robot_state_publisher` 节点的服务拿 URDF。之前后台方式杀的仿真（只 pkill 了 gzserver/gzclient）残留了 launch 进程和它的 robot_state_publisher——那份是加 effort 接口之前的旧描述。gazebo_ros2_control 连上了旧服务，按旧 URDF 注册硬件接口。

**排查特征**
`ps aux | grep robot_state_publisher` 能看到多个实例（launch 本体也可能残留多个 `ros2 launch ... so101_gazebo.launch.py`）。

**解决**
1. 杀掉残留：`kill -9 <旧launch pid> <旧rsp pid>`（只 pkill gzserver 不够）；
2. launch 整体重启（光 `ros2 control load_controller` 重载没用——硬件接口是插件启动时一次性注册的）。

**教训**
后台/被杀的仿真要连 launch 进程一起清：`pkill -f so101_gazebo.launch.py` 再 `pkill -x gzserver; pkill -x gzclient`；怀疑 URDF 没生效时先 `ps aux | grep robot_state_publisher` 数数量。

---

- **改动必验证**：`colcon build --packages-select so101_moveit_gazebo` 后，用 `xacro <顶层文件>` 展开检查（注意 `$(find pkg)` 会解析到 install 目录，改完 src 要先 build 再验证）。
- **重跑 gazebo 前**：`pkill -x gzserver; pkill -x gzclient`。
- **查 Gazebo 私有日志**：launch 终端看不到的 Err/Wrn 在 `~/.gazebo/server-11345/default.log`（物理端）和 `~/.gazebo/client-11345/default.log`（渲染端，mesh 报错多在这），每次启动覆盖，`grep` 时加 `-a`。
- **mesh URI 规则**：URDF/xacro 里 mesh 的 filename 必须带 scheme——RViz 只认 `package://` 和 `file://`，裸绝对路径会报 `Error retrieving file`（Gazebo 无此限制，裸路径能用）。本包统一用 `file://$(find pkg)/...`。
- git 历史关键提交：`81e5c2c`（gazebo 接入+描述宏）、`f62d005`（链式加载控制器）、`d1085f9`（GAZEBO_MODEL_PATH 过渡方案）、`af54e15`（$(find) 绝对路径 + world 固定 + PID）、`ab93113`（暂时移除 PID）。
