# SO101 Gazebo 接入问题排查记录

记录 so101_moveit_gazebo 包在 mock → Gazebo 接入过程中遇到的全部问题：现象、定位过程、解决办法。

环境：ROS 2 Humble + Gazebo Classic 11 + WSL2/WSLg，colcon 工作区 `so101_moveit_gazebo/`。

---

## 1. Gazebo 中机器人"隐形"

**现象**
spawn_entity 日志显示 `Successfully spawned entity [so101]`，但 Gazebo 界面里看不到机器人。

**定位**
URDF 里 mesh 用的是 `package://so101_moveit_gazebo/urdf/assets/xxx.stl`。Gazebo 会把 `package://` 转成 `model://` 再解析，而 Gazebo Classic 只按 `GAZEBO_MODEL_PATH` 找 `model://` 资源，找不到就静默不显示（gzclient 的 `InsertModelWidget.cc: Missing model.config` 报错是线索之一）。

**直接证据（Gazebo 私有日志）**
Gazebo Classic 把全部消息（包括不往 stdout 打的 Err）写进自己的日志文件，不走 ROS 日志系统，所以 launch 终端里看不到任何报错：
```
$ grep -a "Failed to find mesh" ~/.gazebo/server-11345/default.log
[Err] [MeshShape.cc:64] Failed to find mesh file [model://so101_moveit_gazebo/urdf/assets/sts3215_03a_v1.stl]
```
`model://so101_moveit_gazebo/...` 证实了转换机制：spawn 时 `package://` 被转成 `model://`，而包目录不在 `GAZEBO_MODEL_PATH` 里，逐文件解析失败。日志里有 ANSI 转义字节，grep 要加 `-a`。查看方式：
- `~/.gazebo/server-11345/default.log`：gzserver（物理端）；`~/.gazebo/client-11345/default.log`：gzclient（渲染端），mesh 报错多在这里
- `11345` 即启动日志里 `Connected to gazebo master @ http://127.0.0.1:11345` 的端口；每次启动覆盖，可 `tail -f` 实时跟踪

**解决（演进过程）**
1. 先在 launch 里用 `SetEnvironmentVariable` 把包的上级 share 目录加进 `GAZEBO_MODEL_PATH`（提交 `d1085f9`）——能用但污染全局环境；
2. 最终方案：xacro 里 mesh 路径全部写成 `$(find so101_moveit_gazebo)/urdf/assets/xxx.stl`，xacro 展开时直接替换成绝对路径，Gazebo/RViz 都能读，launch 里的环境变量设置也删掉了（提交 `af54e15`）。

## 2. Spawn 失败：`Entity [so101] already exists`

**现象**
```
[spawn_entity]: Spawn status: Entity [so101] already exists.
[spawn_entity]: Spawn service failed. Exiting.
```

**定位**
上一次运行的 gzserver 没退干净，仍占用 11345 端口。新启动的 gzserver 连不上 master 会**静默死亡**（launch 日志里看不到 Gazebo 版本 banner 是明显线索），spawn_entity 连到的是旧实例，旧实例里已经有同名机器人。

**解决**
重跑前清残留进程：
```bash
pkill -x gzserver; pkill -x gzclient
```
注意不要用 `pkill -f`（模式匹配到自己命令行会杀当前 shell），也不要把 pkill 和启动 gazebo 的命令写在同一条里。

## 3. KDL 警告：根链接带惯性

**现象**
robot_state_publisher 启动时：
```
[WARN] [kdl_parser]: The root link base_link has an inertia specified in the URDF,
but KDL does not support a root link with an inertia.
```

**定位**
KDL  kinematics 求解器不允许根链接带惯性属性，而 URDF 的根链接（base_link）写了 `<inertial>`。

**解决**
加一个无质量的虚链接 `world` 作为根，用 fixed 关节把 `base_link` 挂上去。KDL 只限制根链接，非根链接带惯性没问题，警告消除。该修改只加在 `so101_gazebo.urdf.xacro`（Gazebo 版），mock 版保持干净。

## 4. 机器人在 Gazebo 中缓慢"移动"（下沉/歪斜/漂移）

**现象**
机器人能 spawn 出来，但放着不动会逐渐下沉、姿态歪斜，整机像在慢慢移动。

**定位**
URDF 里关节只声明了 `position` 命令接口，而 Gazebo 物理引擎只接受力矩（effort）。`gazebo_ros2_control/GazeboSystem` 内部用一个 PID 把位置误差换算成力矩；**不指定增益时默认值非常弱**，输出的保持力矩抵不过重力，关节被持续拉开。可用 `ros2 topic echo /joint_states` 看到无指令下 position 持续变化来确认。

**解决（当前状态）**
- 在 `<command_interface name="position">` 下加 `<param name="p/i/d">` 可显式指定增益（提交 `af54e15` 加过 p=25, i=0.5, d=5）；
- 应要求暂时移除，先观察 world 固定后的效果（提交 `ab93113`）。
- 调参方向：还下垂→加大 p；振荡/抖动→加大 d；长期静态偏差→加大 i。
- PID 原理：P=弹簧刚度（按误差出力，扛重力主力），I=累积误差补静态偏差，D=阻尼（按误差变化速度刹车防振荡）。

注意：world 固定只解决"整机倾倒/滑动"，**不解决关节下垂**，两者互补。

## 5. RViz 报错：`Package [so101_moveit_gazebo] does not exist`

**现象**
```
[rviz2]: Error retrieving file [package://so101_moveit_gazebo/urdf/assets/xxx.stl]:
Package [so101_moveit_gazebo] does not exist
```

**定位**
两种原因：
1. 运行前没有 `source install/setup.bash`，ament 资源索引里找不到包；
2. mesh 走 `package://` 依赖运行时包查找。

**解决**
每次开新终端先 source 工作空间；mesh 改 `$(find ...)` 绝对路径方案后（问题 2），运行时不再依赖包查找，此问题根治。

## 6. `hold_joints has already been declared` ERROR

**现象**
```
[ERROR] [gazebo_ros2_control]: Parameter 'hold_joints' has already been declared
```

**定位**
包里有 arm、hand 两个 `<ros2_control>` 系统块，都会声明 `hold_joints` 参数，属于 gazebo_ros2_control 的已知现象。

**解决**
无害，忽略。

## 7. gzclient 报 `Missing model.config`

**现象**
```
[Err] [InsertModelWidget.cc:403] Missing model.config for model ".../share/so101_moveit_gazebo"
```

**定位**
Gazebo 客户端扫描 share 目录里可插入的模型，把普通包目录误当模型目录。

**解决**
无害；mesh 改绝对路径方案后此报错也消失。

## 8. Gazebo 界面"卡住"（假死/加载慢）

**现象**
启动后 Gazebo 界面长时间白屏/卡住。

**定位**
WSLg 下 Gazebo 客户端渲染慢，首次加载 mesh/材质更慢，属于性能问题而非死锁。

**解决**
多等一会；日常开发建议不用盯着 Gazebo 界面看模型——用 RViz 看（数据走 TF/joint_states，流畅得多），Gazebo 只当后台物理引擎。

---

## 9. 控制器加载时机：spawn 完成后再起 controller

**现象/背景**
controller_manager 是 `gazebo_ros2_control` 插件在 spawn 之后才启动的，若 launch 里同时 unconditional 加载 controller，会报服务不存在。

**解决**
用 `RegisterEventHandler + OnProcessExit` 链式触发：spawn 退出 → 加载 joint_state_broadcaster → 加载 arm_controller → 加载 gripper_controller。`ros2 control load_controller` 命令本身会等 `/controller_manager` 服务就绪，链式保证顺序即可。用户后来额外加了 `TimerAction(period=10.0)` 延迟 spawn，进一步规避竞争。
